# Deploying to Render (free tier)

One Render **web service** runs everything: gunicorn serves the Flask API, and Flask also serves
the built React app. The repo contains everything Render needs:

| File | What it does |
|---|---|
| `render.yaml` | Blueprint: the service, its build/start commands, health check and environment variables |
| `render-build.sh` | Build: `pip install` the backend, then `npm ci && npm run build` the frontend into `frontend/dist` |
| start command | `python seed.py --keep` (creates the synthetic demo DB if missing), then `gunicorn run:app` |

## What the free tier means for this demo

- **The app sleeps after ~15 minutes without visitors.** The first request afterwards takes about
  a minute while it wakes. Open the URL a minute before a demo.
- **No persistent disk.** Every restart, wake-up or redeploy starts from a fresh synthetic database.
  New sign-ups, uploads, messages and edits disappear when that happens. The seeded demo data
  is always there and always clean.
- To keep data, upgrade the service to **Starter** and add a **Disk** mounted at `/var/data`,
  then set `DATABASE_PATH=/var/data/onboarding.db` and `UPLOAD_DIR=/var/data/uploads`.

## Steps

### 1. Put the code on GitHub

The repo must not contain secrets. `.gitignore` already excludes `backend/.env`, the local
database (`backend/db/*.db`), uploads, `node_modules`, `.venv` and `frontend/dist`.

```bash
cd customer-onboarding
git init -b main
git add .
git status            # check: no .env, no onboarding.db, no uploads
git commit -m "Project 040 – Customer Onboarding Checklist Assistant"
```

Create an empty repository on GitHub (private is fine; Render can read private repos), then:

```bash
git remote add origin https://github.com/<you>/customer-onboarding.git
git push -u origin main
```

### 2. Create the service on Render

1. Sign in at <https://dashboard.render.com> with GitHub.
2. **New → Blueprint**, pick the `customer-onboarding` repository and branch `main`.
3. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable | What to enter |
   |---|---|
   | `GEMINI_API_KEY` | Your Gemini API key (paste only here, never in git) |
   | `ADMIN_EMAIL` | The officer login, e.g. `officer@yourdomain.test` |
   | `ADMIN_PASSWORD` | A strong password (min 8 chars, a letter and a number) |
   | `DEMO_ACCESS_CODE` | A short code you give reviewers. AI features ask for it, so strangers can't spend your Gemini quota |

   `SECRET_KEY` is generated by Render. Everything else has a default in `render.yaml`.
4. Click **Apply**. The first build takes about 3–5 minutes.

### 3. Check it works

1. Open `https://customer-onboarding-XXXX.onrender.com/api/health`. It should show
   `"status":"ok"`, `"database":"ok"` and `"llm":{"configured":true,"provider":"gemini"}`.
2. Open the site root and sign in on the **Staff** tab with `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
3. On the **Learner** tab, try **Explore the demo learner account** (read-only).
4. Sign up as a new learner and upload a document to check uploads work.
5. In the admin portal, run an AI action (e.g. draft a reminder). Enter `DEMO_ACCESS_CODE` when asked.

### 4. Updating

Every `git push` to `main` redeploys automatically (`autoDeploy: true`). A redeploy resets the
demo database (see above).

## Troubleshooting

| Symptom | Fix |
|---|---|
| Build fails with "npm is not available" | Change the service to Docker, or commit a built `frontend/dist` and remove the npm lines from `render-build.sh` |
| Health shows `"llm":{"configured":false}` | `GEMINI_API_KEY` is missing. Add it under **Environment**, then **Manual Deploy → Deploy latest commit** |
| Can't sign in as staff | `ADMIN_PASSWORD` was empty when the DB was seeded, so a random one was printed in the **Logs**. Set it and redeploy |
| AI requests time out | Gemini is slow or the key's quota is used up. The app falls back to a clearly labelled template |

The local `admin@demo.test` login exists only in your local database and is never deployed.
